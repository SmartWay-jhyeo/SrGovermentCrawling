# 최근 3개년 백필(완전 수집)

작성: 2026-09-16 (KST)

## 목적

도장·습식·방수·석공사업 관련 공사 공고를 최근 3개년 범위에서 후보 필터에 걸린 목록을 **표본 없이 전부** 받아 원본을 누적 저장하고, 누적 데이터 전체로 통계를 낸다. 일일 API 한도 안에서 여러 날에 걸쳐 수집하며, 중단되면 다음 실행이 마지막 위치부터 이어간다.

## 명령

```powershell
.venv\Scripts\python -m bidloc backfill init           # job·기간 파티션 생성(범위 고정)
.venv\Scripts\python -m bidloc backfill run --live     # 수집(recall 게이트 통과 필요). 매일 다시 실행하면 이어서 수집
.venv\Scripts\python -m bidloc backfill recall-check --live   # 후보 필터 recall 측정(--study-config 로 추가 표본)
.venv\Scripts\python -m bidloc backfill recall-report         # recall 결과(네트워크 없음)
.venv\Scripts\python -m bidloc backfill status         # 파티션·작업 큐·오늘 API별 사용량
.venv\Scripts\python -m bidloc backfill stats          # 누적 데이터로 통계(CSV·JSON, Git 제외 경로)
```

- `run`은 `.env`의 `ALLOW_LIVE_API=true`, 인증키, CLI `--live`가 모두 있어야 호출한다.
- `--max-calls N`은 이번 실행 전체 상한이다(선택). API별 일일 한도는 항상 따로 적용된다.
- 한 실행은 모든 서비스가 오늘 한도에 닿거나 처리할 일이 없을 때 끝난다. 두 서비스가 800회씩 쓰면 요청 간격 1초 기준 약 30분 걸린다.
- 매일 자동 실행: 2026-09-18 사용자 요청으로 Windows 작업 스케줄러에 등록했다(아래 절). 저장소 파일은 스케줄을 만들지 않는다.

### 명령

```powershell
.venv\Scripts\python -m bidloc backfill sweep-init          # 단계별 하루 파티션 생성(범위 고정)
.venv\Scripts\python -m bidloc backfill sweep-run --live    # 수집. 매일 다시 실행하면 이어서 수집
.venv\Scripts\python -m bidloc backfill sweep-status        # 단계별 파티션·수신 행·오늘 사용량
.venv\Scripts\python -m bidloc backfill sweep-finalize      # 관련성 확정(네트워크 없음)
```

- job `sweep-3y:2023-09-20:2026-09-19`, 단계 4개 × 하루 파티션 1,096개 = 4,384개.
- 구간 끝은 다음 구간 시작과 1분 겹치고, 행은 키로 중복 제거된다.
- 페이지 도중 `totalCount`가 달라지거나 수신 행이 안 맞으면 그 하루를 1페이지부터 다시 받는다(최대 3회).
- 서비스마다 자기 단계를 순서대로(LIST → LICENSE → REGION) 처리하고, 서비스끼리는 번갈아 진행한다. 한 서비스가 한도에 닿아도 다른 서비스는 계속한다.

### 관련성 판정 (`sweep-finalize`, 호출 없음)

- 면허제한 행에 목표 코드가 있으면 RELEVANT. 코드 컬럼은 정확히 비교하고, 허용업종목록은 숫자 토큰으로 끊어 비교한다(`49920` 같은 부분일치 제외).
- 면허 단계가 **끝나기 전에는 RELEVANT만 표시**한다. 아직 안 받은 행을 '없음'으로 단정하지 않기 위해서다.
- 면허 단계 완료 후: 행은 있는데 목표 코드가 없으면 NOT_RELEVANT, 행 자체가 없으면 UNKNOWN(참가불가로 보지 않는다).
- 취소공고(목록 `ntceKindNm`에 취소)는 그대로 CANCELLED로 둔다.

### 이전 방식 (공고당 상세 호출) — 참고용으로 남김


| 단계 | API(오퍼레이션) | 대상 | 커서 |
|---|---|---|---|
| LIST | 입찰공고 `getBidPblancListInfoCnstwkPPSSrch` (`inqryDiv=1`, 후보 필터: recall 검증 결과에 따라 결정) | 7일 파티션 × 전체 페이지(100행) | `bf_partition.next_page` |
| LICENSE | 입찰공고 `getBidPblancListInfoLicenseLimit` | 목록에 나온 공고의 최신 차수. 취소공고는 호출 안 함 | `bf_task` |
| REGION | 입찰공고 `getBidPblancListInfoPrtcptPsblRgn` | 면허제한에 4992가 있는 공고(RELEVANT)와 해석 미확인(UNKNOWN) | `bf_task` |
| OPENING | 낙찰정보 `getOpengResultListInfoCnstwk` | 위와 같음 + 취소 아님 + 개찰일시 다음 날 이후 | `bf_task` |
| AWARD / ROSTER | 낙찰 목록 / 개찰 명부 | 기본 끔(`config/backfill.yaml`) | `bf_task` |

- 목록 단계가 후보를 거르고, 면허제한 단계가 관련성을 확정한 뒤에만 지역·개찰을 부른다. 면허제한에 4992가 없는 공고(NOT_RELEVANT)는 지역·개찰을 호출하지 않는다.
- 공고에 새 차수가 나오면 이전 차수의 대기 작업은 "새 공고차수로 대체"로 건너뛰고 최신 차수로 다시 받는다. 취소공고가 보이면 그 공고의 남은 작업은 모두 건너뛴다.
- 개찰결과가 0건이면 개찰일시 후 14일 안에는 최대 3회까지 미뤄서 다시 확인하고, 그 뒤에는 "개찰기록 없음"으로 끝낸다. 참여 0으로 기록하지 않는다.
- 단계들은 번갈아 한 건씩 처리한다. 같은 서비스의 단계는 하나의 일일 예산을 나눠 쓰고, 한 서비스가 한도에 닿아도 다른 서비스는 계속 진행한다.
- 면허제한 조회 결과(recall 측정에서 받은 것 포함)는 `bf_license_fetch`에 남아 같은 공고·차수는 다시 호출하지 않는다.

## 일일 한도 (서비스 단위 합산)

- 포털은 트래픽을 OpenAPI 서비스 단위로 표기한다("신청 가능 트래픽 개발계정 : 1,000"). 참고자료 오류코드 22 설명의 "서비스 상세기능별 일일 트래픽량" 문구는 있지만, 게이트웨이가 오퍼레이션별로 독립 할당한다는 실측 증거는 없다.
- 그래서 기본값은 **서비스 단위 합산**이다(`BACKFILL_QUOTA_SCOPE=service`, `BACKFILL_MAX_CALLS_PER_SERVICE_PER_DAY=800`).
  - 입찰공고정보서비스(`bid_notice`): 목록 + 면허제한 + 참가가능지역(+ 기초금액 등) 호출 합계 ≤ 800
  - 낙찰정보서비스(`bid_award`): 개찰결과 + 개찰순위 명부 + 낙찰 목록 호출 합계 ≤ 800
- 사용량 = 그날(KST) `source_response`에 기록된 해당 서비스의 실제 시도 수와 `api_daily_usage` 예약 카운터 중 큰 값. verify-api·backfill·recall 측정 호출이 모두 합산된다.
- `BACKFILL_QUOTA_SCOPE=operation`은 오퍼레이션별 독립 한도가 실제 호출 결과나 공식 문서로 확인된 경우에만 쓴다.
- 예약은 전송 전에 하고 재시도·실패도 센다. 제공기관 일일 한도 오류(22)를 받으면 그 서비스 전체를 그날 멈춘다.
- 이전 버전(2026-09-16)은 오퍼레이션별 800회를 가정했다. 2026-09-16 실제 호출을 서비스 합산으로 다시 세면 입찰공고정보서비스 67회, 낙찰정보서비스 27회, 업종 서비스 2회였다(모두 800 이하).

## 재개 규칙

- 범위는 `backfill init`(또는 첫 `run`) 시점에 고정된다: 시작일 = 생성일 − 3년, 끝일 = 생성일 전날. 2026-09-16 생성 job: `dojang-seupsik-3y:2023-09-16:2026-09-15`, 파티션 157개.
- 목록: 진행 중 파티션의 `next_page`부터 받는다. 페이지 도중 `totalCount`가 바뀌거나 받은 행 수가 `totalCount`와 다르면 파티션을 1페이지부터 다시 받는다(최대 3회). 파티션 경계는 1분 겹치고 공고 키로 중복 제거한다.
- 상세: `PENDING` → 기한 된 `DEFERRED` → 시도 3회 미만 `FAILED` 순으로 집는다. 여러 페이지 작업이 도중에 한도에 걸리면 작업 상태를 바꾸지 않고 다음 날 처음부터 다시 받는다.
- 모든 커밋은 작업 단위라 강제 종료해도 완료분은 남는다.

## 저장

- 원본: 모든 응답 본문을 `.local/real/raw/`에, 요청·결과 메타데이터를 `source_response`에 누적한다(키 마스킹).
- 누적 해석 테이블: `bf_notice_revision`(공고번호+차수), `bf_license_limit`, `bf_allowed_region`, `bf_opening_unit`(네 키), `bf_award`, `bf_roster_row`, `bf_notice_state`(관련성).
- 같은 키로 내용이 달라진 응답은 덮어쓰기 전에 `bf_record_conflict`에 이전 값을 남긴다.
- 면허제한 행의 필드 밀림(등록일시 형식 아님, 목록 필드가 대괄호 아님)은 `quality_flag`로 표시하고, 목표 코드가 안 보이면 NOT_RELEVANT 대신 UNKNOWN으로 둔다.
